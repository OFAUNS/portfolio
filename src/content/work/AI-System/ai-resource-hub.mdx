# AI 資源整合 App

>AI 工具越用越多之後，真正的問題不是「哪個模型比較強」，
而是「我上次那個好用的提示詞放在哪」「這個月到底花了多少錢」
「換一家供應商要改幾個地方」。
這個 App 處理的是資源分散造成的管理成本，不是模型能力本身。

## 一層調度，四類資源

架構的核心是中間那層統一調度層。所有資源都往它註冊，所有呼叫都經過它出去，
上層的工作流因此不需要知道底下實際用的是哪一家供應商。

**模型供應商**　多家 API 被收斂成同一個介面，換供應商是換註冊設定，不是改動上層流程。

**提示詞庫**　提示詞被當成可版本化的資產管理，改壞了可以回溯上一版，好用的可以標記共用。

**工具與外掛**　MCP 服務與本機腳本一起註冊進來，讓「要開另一個程式才能做的事」回到同一個入口。

**知識來源**　檔案、筆記與外部資料以來源為單位掛載，需要時才被帶進上下文。

## 憑證與成本為什麼要放在同一層

把金鑰散在各支腳本自己的設定檔裡，短期最快，長期會變成沒有人敢動的地雷區——
你不知道哪支腳本還在用哪把過期的鑰匙。集中在調度層之後，換鑰匙是一個動作，
而不是全專案搜尋。

用量同理。分散呼叫的結果是月底帳單來了才知道花在哪，而且拆不出來。
把計量放在唯一的出口，成本才有辦法即時顯示在入口畫面上，
超過門檻時當下就提示，不必事後對帳。

## 這個設計的取捨

統一調度層是一個明確的單點——它壞掉的時候，所有東西一起停。
換來的是上層流程完全不需要處理供應商差異，以及一個真的說得出「現在有哪些資源、
分別花了多少」的地方。以個人與小團隊的使用規模來說，這個取捨是划算的；
規模再大就要另外處理這一層的可用性。
